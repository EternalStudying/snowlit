# Drafts: autosaved albums, diary entries and moments

Status: agreed with the product owner on 2026-10-20 (decision log at the end). To be implemented by another agent and reviewed afterwards against this document.

## 1. Problem

A member who leaves the mini program by accident (a call, a swipe, WeChat killing the page) loses what they were creating. For albums this is worst: every picked photo has to be picked and uploaded again. Diary text and moment fields are lost the same way.

## 2. Solution in one paragraph

Every member has at most one **draft** per kind (album, diary entry, moment) stored on the server in one `drafts` table. In the mini program, creating a new album, diary entry or moment autosaves: the draft is created on the first change, each picked photo uploads into the draft at once, and text fields save shortly after typing stops and immediately when the page hides. Opening the same "new" page later asks whether to continue the draft or discard it. Publishing turns the draft into the real album, diary entry or moment and deletes the draft. Album drafts, which today are album rows with status `draft`, move into the same table; the web client's existing album draft flow moves to the new API.

## 4. Vocabulary

Update `GLOSSARY.md`: replace **Draft album** with:

> **Draft**:
> A member's unpublished album, diary entry or moment, saved on the server as they create it; at most one per member per kind. Publishing turns it into the real record and removes the draft.
> _Avoid_: temporary album, upload session, autosave record

> **Draft image**:
> A photo uploaded into a draft before publishing; owned by the draft, deleted with it if the draft is discarded or the image is not used at publish.

Use "draft" in code (`Draft`, `drafts`, `draftId`), never "temp" or "session".

## 5. Data model

### 5.1 Table (add to `backend/src/main/resources/schema.sql`, after `moments`)

```sql
create table if not exists drafts (
    id bigint primary key auto_increment comment '草稿主键',
    user_id bigint not null comment '草稿所属用户 ID',
    kind varchar(20) not null comment '草稿类型：album、diary 或 moment',
    fields_json text not null comment '客户端可写的表单字段 JSON 对象',
    images_json mediumtext not null comment '服务端维护的草稿图片 JSON 数组',
    created_at datetime not null comment '创建时间',
    updated_at datetime not null comment '最近保存时间',
    constraint fk_drafts_user foreign key (user_id) references users(id) on delete cascade,
    unique key uq_drafts_user_kind (user_id, kind)
) comment='创建中的相册、日记与点滴草稿';
```

`schema.sql` is the only SQL file to change. No migration tool and no separate migration file (owner's decision). Do not change `albums`, `photos`, `diaries`, `diary_uploads` or `moments`. The `albums.status` column stays; after this change no code writes `draft` into it.

### 5.2 `fields_json`: owned by the client, replaced whole on every save

Every field is optional while drafting. Types mirror the create request of each kind; unknown keys are rejected (`DRAFT_FIELDS_INVALID`). Limits match the target tables, so nothing saved can fail later for length alone.

| Kind | Fields |
|---|---|
| `album` | `title` (≤120), `description` (≤500), `eventDate` (`YYYY-MM-DD`), `location` (≤120), `visibility` (`public`/`private`), `pinned` (boolean). **Never** `privatePassword`. |
| `diary` | `contentMarkdown` (≤ 60,000 characters; the diary create path has no length rule today, the `text` column holds 64 KB), `date` (`YYYY-MM-DD`), `moodKey`, `visibility` (`shared`/`private`), `weatherSnapshot` (same shape as `DiaryWeatherSnapshotDto`). |
| `moment` | `title` (≤160), `content`, `eventTime`, `endTime` (ISO local date-time), `locationName` (≤160), `address` (≤300), `longitude`, `latitude`, `category` (`daily`/`date`/`travel`/`anniversary`/`surprise`). Image URLs are **not** a field; they come from the draft's images. |

Enumerated values are validated when present. Required-ness is checked only at publish.

### 5.3 `images_json`: owned by the server, never written by the client

An ordered array (upload order) of:

```json
{
  "id": "d7f3…",            // server-generated, opaque, unique within the draft
  "url": "…",               // display URL (album: preview URL)
  "objectName": "…",        // never returned to clients
  "contentType": "image/jpeg",
  "sizeBytes": 123456,
  "original": { "url": "…", "objectName": "…", "contentType": "…", "sizeBytes": 0 },  // album only
  "width": 4032, "height": 3024,   // album only
  "takenAt": "2026-05-20",         // album only, optional
  "location": "…",                 // album only, optional
  "caption": "…"                   // album only, optional
}
```

`objectName` values exist only server-side. Every delete goes through these stored names, so a client can never make the server delete an object it names.

## 6. Backend

### 6.1 Module

Add a `xyz.snowlit.draft` package: `DraftController`, `DraftModule`, `DraftMapper` (MyBatis annotations like the other mappers), `Draft`, `DraftDtos`, `DraftVos`, `DraftKind` (enum `ALBUM`, `DIARY`, `MOMENT`; path value is the lower-case name).

- **One module owns the lifecycle**: read, save, upload, remove an image, discard, publish. It calls into the album, diary and story modules to create the real record. Those modules expose a narrow "create from a draft" entry point rather than having the draft module write their tables directly.
- **Authorization:**
  - `album` and `moment`: managers only. Use `actor.requireManager` with the existing codes: `ALBUM_FORBIDDEN` ("只有站点主人可以管理相册") and `STORY_FORBIDDEN` ("只有站点主人可以管理点滴").
  - `diary`: any signed-in member with a couple role. Use the diary module's existing role resolution; a missing role fails as it does today.
  - A member only ever sees and changes their own drafts. There is no draft id in any URL; the draft is always `(actor.userId, kind)`.

### 6.2 API (`/api/drafts/{kind}`)

| Method and path | Body | Result | Notes |
|---|---|---|---|
| `GET /api/drafts/{kind}` | | `{ "draft": Draft \| null }` | |
| `PUT /api/drafts/{kind}` | `{ "fields": {…} }` | `Draft` | Creates the draft if missing (upsert), replaces `fields_json`, updates `updated_at`. |
| `DELETE /api/drafts/{kind}` | | 204 | Deletes all draft images (best effort, after the row is gone), then the row. 204 also when no draft exists. |
| `POST /api/drafts/{kind}/images` | multipart (below) | `DraftImage` | Creates the draft with empty fields if missing. |
| `DELETE /api/drafts/{kind}/images/{imageId}` | | 204 | Removes the entry and deletes its objects. 404 `DRAFT_IMAGE_NOT_FOUND` if absent. |
| `POST /api/drafts/{kind}/publish` | `{ "fields": {…}, "privatePassword": "…" }` | kind-specific (below) | `fields` are the client's latest values and are saved first, so a pending debounced save can't be lost. `privatePassword` is album only and never stored. |

`Draft` VO: `{ kind, fields, images: DraftImage[], createdAt, updatedAt }`. `DraftImage` VO: `{ id, url, width?, height?, takenAt?, location?, caption?, originalUrl? }`. Never include object names.

Upload multipart per kind:

- `album`, mini program: `file` + `metadata` (JSON `{caption, takenAt, location, width, height}`). Stored with the existing mobile rule: one file serves as original and preview, as `uploadMobilePhoto` does today.
- `album`, web: `original` + `preview` + `metadata`. Same verification and policies as today's web upload (`ORIGINAL_IMAGE` plus the WebP `PREVIEW_IMAGE` rule).
- `diary`, `moment`: `file`. Use the kind's existing `ImagePolicy` (diary `IMAGE`, story `IMAGE`) and storage path rules, so URLs look exactly like today's.
- Reuse `ImageIntake.verify` / `store`. On a failure after storing, delete what was stored (best effort), as `addPhoto` does now.
- Limits are counted on the draft's images: album 300 (backend `MAX_PHOTOS`; the mini program keeps its own 9-photo limit), diary 20, moment 3. Exceeding a limit returns the kind's existing code: `ALBUM_PHOTO_LIMIT_EXCEEDED`, `DIARY_IMAGE_LIMIT_EXCEEDED` or `STORY_IMAGE_LIMIT_EXCEEDED`.

Concurrent saves: **last save wins** (owner's decision). Image list changes (upload, remove) must not lose each other. Do them under a row lock (`select … for update` inside a transaction) or as an atomic JSON update. A fields `PUT` replaces only `fields_json` and never touches `images_json`.

### 6.3 Publish, per kind

Each publish runs in one transaction:
1. Save `fields`.
2. Validate everything the kind's create endpoint validates today (same error codes and messages).
3. Create the real record from the draft.
4. Delete the draft row.

Object deletions happen **after commit**, best effort. On any validation or conflict error nothing is created and the draft stays exactly as saved, including the newly sent fields.

- **album**
  - Validate with today's `validateCreateRequest`. The title is required at publish (`ALBUM_TITLE_REQUIRED`), and a private album needs `privatePassword` (`ALBUM_PRIVATE_PASSWORD_REQUIRED`).
  - Require at least 1 image (`ALBUM_PHOTO_REQUIRED`).
  - Insert the `albums` row with status `published` and `published_at` = now. Insert one `photos` row per draft image, in order, carrying today's metadata, original/preview URLs and object names. The cover is the first photo's preview URL.
  - Return the same shape the old publish returned: `{ album: AlbumVo, photos: AlbumPhotoVo[] }`.
- **diary**
  - Validate with today's create validation, including `DIARY_DAY_ALREADY_EXISTS` for a role and date that already has an entry. The draft stays, so the member can change the date.
  - Every image URL in `contentMarkdown` must be one of the draft's images (`DIARY_IMAGE_FORBIDDEN` otherwise).
  - For each referenced draft image, insert a `diary_uploads` row (`temporary = false`, `promoted_at` = now) and its `diary_images` reference.
  - Draft images not referenced in the markdown are deleted after commit.
  - Return today's `DiarySummaryVo`.
  - **Important:** draft images never enter `diary_uploads` before publish. The hourly `cleanupExpiredTemporaryImages` job deletes unreferenced temporary uploads after 6 hours, so it can't touch them.
- **moment**
  - Validate with today's story create validation.
  - `images` = the draft's image URLs in order, at most 3.
  - Return today's `StoryMomentVo`.

### 6.5 Errors

New codes (Chinese messages in the house tone):

| Code | Status | When |
|---|---|---|
| `DRAFT_KIND_INVALID` | 404 | `{kind}` is not album, diary or moment |
| `DRAFT_FIELDS_INVALID` | 400 | Unknown key, wrong type, bad enum value or over-length field |
| `DRAFT_NOT_FOUND` | 404 | Publish without a draft |
| `DRAFT_IMAGE_NOT_FOUND` | 404 | Removing an image id the draft doesn't have |

Everything else reuses the existing codes of the target kind.

## 8. Mini program (`miniprogram/`)

### 8.1 Service

Pages never build URLs (technical-spec rule). Remove the album draft functions from `services/album.js`.

### 8.2 Shared autosave behaviour (one helper, used by all three pages)

Put the shared behaviour in one small module (e.g. `utils/draft-autosave.js`) rather than three copies. It takes the kind, a `read()` of the current fields, and a `view` callback for status; it exposes `changed()`, `flush()` and `stop()`.

- **Applies only to new entries.** Diary and moment edit mode (an existing id) never use drafts.
- **On page load (new entry mode):** call `getDraft(kind)`.
  - If a draft exists, show `showConfirm` with title "继续上次的草稿？", content showing when it was last saved (e.g. "上次保存于 10月20日 21:14"), confirm "继续编辑" and cancel "放弃草稿".
  - 继续编辑 fills the form and image list from the draft.
  - 放弃草稿 calls `discardDraft` and starts an empty form.
  - While the dialog is open, the form stays locked.
- **First change creates the draft.** Any field edit or photo pick counts.
- **Text and field changes:** `saveDraft` 1500 ms after the last change, with one save in flight at a time; a change during a save schedules one more.
- **Flushing:** `onHide` and `onUnload` flush immediately (no debounce). This covers the accidental-exit case.
- **Photos:** upload on pick through `uploadDraftImage`, using the existing `pickImages` and `uploadQueue`. Each image's local state shows its upload progress as today. Removing an image calls `removeDraftImage` once it has a server id.
- **Status line:** a small, quiet caption near the footer: "已自动保存 21:14", "保存中…", or "自动保存失败，稍后会重试". A failed save never blocks typing and is retried on the next change or flush. No toast for autosave.
- **Publishing:**
  - The existing primary button keeps its label (保存相册 / 保存日记 / 发布点滴). It calls `publishDraft(kind, fields, { privatePassword })` and waits for uploads in flight first, as save does today.
  - On success: the draft is gone, the page shows its success message and navigates as today.
  - On error: show the message; the draft stays.
- **Session change:** drafts are per member. If the business token changes (logout, another member) while a page is open, stop autosave and drop the page state (use `beginRequest` from `utils/request-guard.js` for draft requests).

## 9. Rolling out to an existing database (not your task; for context)

Retained databases run with `SQL_INIT_MODE=never`, so the new table is not created automatically. The reviewer will, with the owner's go-ahead and after a backup:

1. Count album rows with `status = 'draft'` (read-only) and report the number.
2. Run the `create table if not exists drafts …` statement.
3. Convert each draft album and its photos into a `drafts` row of kind `album`:
   - album fields go into `fields_json`; there is no password;
   - photos go into `images_json`, with object names and URLs unchanged;
   - then delete the old draft album row, and its photos with it, by cascade.

Make sure the code works with **any** `images_json` built this way: an album image whose `original` equals its `url` (mobile uploads) must publish correctly.
